# AGENTS.md — working on the AI Sandbox control app

What a coding agent needs to change this repository. The user-facing docs are in [README.md](README.md).

## Layout

| Path | |
|---|---|
| `src/main.rs`, `src/lib.rs` | Entry point; `lib::run` dispatches the commands |
| `src/cli.rs` | Every command and option as one clap `enum` (an unhandled command doesn't compile) |
| `src/commands/` | `lifecycle` (up/stop/down/…), `network` (allow/deny/blocked/reload), `llm`, `maintenance` (init/info/rebuild/…), `upgrade` (self-update from GitHub releases) |
| `src/config/` | Reads and validates `sandbox.toml` / `sandbox.local.toml` (`reader.rs`: typed table access) |
| `src/compose.rs` | Renders `resources/compose.yml.j2` (MiniJinja) into `.state/compose.yml` |
| `src/engine/` | Writes the embedded `resources/` into `.state/desktop/`,`.state/proxy/`,`.state/llm/`; `manifest.rs` tracks what was written|
| `src/project.rs` | Finds `.sandbox/`, the stable id, old-layout warnings (`engine/`, `sandbox.yml`) |
| `src/runtime/` | The container runtime: `trait Runtime` (`mod.rs`: every container operation the commands use, mostly default methods; `select` picks Docker or Podman), `docker.rs`, `podman.rs`, `ps.rs` (`compose ps` JSON) |
| `src/process.rs` | Running programs (captured or attached), the browser, the host user's ids |
| `src/allowlist.rs` | Line-based edits of `allowlist.txt` that keep comments and groups |
| `src/ui/` | Terminal output (panels, tables) |
| `resources/` | The engine, compiled into the binary: compose template, Dockerfiles, tool scripts, proxy and LLM gateway config, `init/` templates |
| `tests/` | End-to-end tests against a fake `docker` (see [tests/README.md](tests/README.md)) |
| `install/` | `install.sh` / `install.ps1`: download a release, verify `SHA256SUMS`, put `sandbox` on PATH |
| `.github/` | `workflows/test.yml` (tests), `workflows/release.yml` (releases); `cliff.toml` (changelog and version rules) is in the root |
| `doc/plans/` | Design plans: start with a `> **Status:**` line, end with an *As built* section written by the implementer |

`build.rs` sets the version (`<version>+<commit>`: `SANDBOX_RELEASE_VERSION`, else the newest `vX.Y.Z` tag, else the crate
version), `SANDBOX_TARGET`, `SANDBOX_RELEASE_BUILD` (only with `SANDBOX_RELEASE_VERSION`), and rebuilds when `resources/` changes.

## Build and test

```bash
cargo build
cargo test --workspace --all-targets --locked   # what CI runs (.github/workflows/test.yml)
cargo clippy --all-targets
```

The end-to-end tests are the specification: they run the built `sandbox` binary against `fake-docker` and assert the
exact docker calls, exit codes, messages and the generated compose file. No Docker needed. Behaviour changes need a test
there; pure logic gets unit tests in `#[cfg(test)] mod tests` in its module.

## How it works

- **Launchers.** `sandbox` / `sandbox.ps1` run `cargo run --quiet --locked --manifest-path <repo>/Cargo.toml --bin sandbox -- <args>`
  with `SANDBOX_DIR` set to the `.sandbox` folder next to them. Without `SANDBOX_DIR` the app searches upwards from the
  current directory for a `.sandbox` folder.
- **Order of side effects** (asserted by the tests): `claude` is handled before argument parsing (all its arguments
  belong to claude); `init`, `allowlist`, `info` and `upgrade` need no container runtime (`upgrade` no project); every other command loads the project,
  selects the runtime, checks it, refuses a container group owned by another project, syncs the engine and regenerates `compose.yml`.
- **Runtime.** `SANDBOX_RUNTIME`, else `[host] runtime` (`auto` | `docker` | `podman`); `auto` = Podman if `podman` is on
  PATH, else Docker. Commands get `ui: &Ui` and a `&dyn Runtime` and call its operations (the `Ui` is passed to every operation that runs a program, never stored); only what differs is overridden in
  `docker.rs` / `podman.rs` (Podman: no `--ansi` flag but `COMPOSE_ANSI`, `podman info` format, `index .Labels`,
  the NVIDIA CDI check before `up`). `podman compose` must delegate to docker-compose: Podman's `check_running` runs
  `podman compose version` and refuses podman-compose, which lacks `--project-directory`, `up --wait` and `ps -a`.
  The template gets `host.runtime` and `host.rootless` (keep-id, SELinux `z`, CDI GPU). The e2e tests set `SANDBOX_RUNTIME=docker` unless a test chooses otherwise.
- **Engine sync.** Every file under `resources/desktop|proxy|llm/` is written with a header (`Generated by sandbox
  <version> — changes are overwritten. Settings: sandbox.toml.`) where the format allows comments. Missing files are
  written; matching files are left alone; files that still hold what the last run wrote (per `.state/.manifest`) are
  updated silently; files that differ from both were edited by hand and are restored with a warning. Leftover files are
  deleted, nothing else in `.state/` is touched. The manifest is written last, so every step is idempotent.
- **Compose.** The template gets the settings plus host facts (user ids, time zone, mounts, UI port). The UI port, the
  project mounts, the `.sandbox` mount and the proxy settings come from the template only, so nothing in
  `sandbox.toml` can change them. `protect_sandbox`: `"hide"` mounts the empty `.state/empty/` (emptied on every run)
  read-only over `.sandbox` (not a tmpfs: Podman copies what is under a tmpfs into it, `tmpcopyup`), `true` mounts it
  read-only; it is never writable (`false` is an error).
- **Settings.** Unknown sections/keys/tools, wrong types and invalid values are errors that list the valid names.
  `sandbox.local.toml` may only hold `[host]` and `[llm]`; within `[llm]`, `gpu` is local-only and `models` /
  `keep_alive` are `sandbox.toml`-only. Reserved environment names (`RESERVED_ENV` in `src/config/mod.rs`) are
  rejected in `[env]`, with a pointer to the key that sets them.
- **Tools.** `resources/desktop/Dockerfile` has one `ARG INSTALL_<TOOL>` + `RUN sandbox-install <tool>` pair per tool;
  the app reads the `ARG INSTALL_*` lines as the list of known tools. A new tool needs `resources/desktop/tools/<name>.sh`,
  that pair, and its hosts as a commented group in `resources/init/allowlist.txt`.
- **Local LLM.** Ollama (`ollama/ollama`, the `-rocm` tag for AMD) on an internal network, behind an nginx gateway
  (`resources/llm/`) that only passes inference and read-only routes and logs usage (`usage.js`, QuickJS). Models live
  in the machine-wide volume `sandbox-llm-models`, which `down`, `reset-home` and engine updates must never touch.
- **Nested sandboxes.** `[tools] podman` (`tools/podman.sh`) installs rootless Podman + docker-compose-v2 in the
  desktop, with `newuidmap`/`newgidmap` given file capabilities (setuid root would need CAP_SYS_ADMIN), a
  `containers.conf.d` drop-in (`utsns = "host"`: the seccomp profile blocks `sethostname`), and two s6 services
  as `abc`: the API socket for docker-compose and `sandbox-podman-health` (healthchecks; there is no systemd).
  `custom-cont-init.d/60-podman` writes abc's subuids from the container's id map. The app (`engine/compose.rs`)
  requires rootless Podman for the tool (`check_nesting`) and sets `host.nesting`: `/dev/fuse`, `/dev/net/tun`,
  `label=disable`, `unmask=ALL`, pids 32768, the `containers` volume, `SANDBOX_INSIDE=1`. With `SANDBOX_INSIDE=1`
  the app is nested (`project::inside_sandbox`): `.state/` must be writable (`check_writable`), `[llm]` is dropped
  (`llm_off_nested`), and `host.nested` runs the proxy with `tinyproxy-nested.conf` (`Upstream` to
  `sandbox-upstream`, the outer proxy's IP resolved from `$HTTPS_PROXY`), without `hostname` and host-gateway, and builds the images with
  `http_proxy`/`https_proxy` build args (`x-build-proxy`): docker-compose passes only the uppercase names from
  `~/.docker/config.json`, which `60-podman` fills in, and apt reads only the lowercase ones.

## Releases

Every push to `main` runs `.github/workflows/release.yml`: the tests, then git-cliff for the next version and the
notes, then the builds, then a GitHub release `vX.Y.Z`. Git tags are the only version record; Cargo.toml stays at its
first version and nothing is committed back.

- **Commit messages follow [Conventional Commits](https://www.conventionalcommits.org)**, e.g.
  `feat(llm): pull models in parallel`, `fix: keep comments in allowlist.txt`. With squash merges the PR title is the
  commit message, so it must follow it too.
- **Version and sections** (rules in `cliff.toml`): `feat` → Added, minor; `fix` → Fixed, patch; `refactor`/`perf` →
  Changed, patch; `docs`/`test`/`ci`/`build`/`chore`/`style` → not listed, no release on their own; `!` after the type
  or a `BREAKING CHANGE:` footer → major (minor while the version is 0.x). Anything unconventional lands under Other
  and counts as a patch. Dry run: `git cliff --bumped-version` and `git cliff --unreleased --bump`.
- **Changelog**: the release notes are that release's section; the full `CHANGELOG.md` is a release asset.
- **Targets**: `x86_64`/`aarch64-unknown-linux-musl` (static), `x86_64-pc-windows-msvc`, `aarch64`/`x86_64-apple-darwin`.
  Assets per target: `sandbox-<target>.tar.gz|.zip` (binary, README, LICENSE, for the install scripts) and the raw
  binary `sandbox-<target>[.exe]` (for `sandbox upgrade`), plus `SHA256SUMS`, `VERSION`, `CHANGELOG.md` and both install
  scripts. The names carry no version so `releases/latest/download/<name>` stays valid.
- **`sandbox upgrade`** (`src/commands/upgrade.rs`) reads `VERSION`, downloads the binary and `SHA256SUMS`, verifies and
  replaces itself (`self-replace`). `SANDBOX_RELEASE_URL` points it at another releases URL (tests, forks).

## Conventions

- Keep the README, the `init` templates (`resources/init/`) and the code in step: a new key, command or message goes
  everywhere it is described.
- Error messages say what to do (`Set name under [project] in sandbox.toml.`).
- `resources/**` and the `sandbox` launcher are LF (`.gitattributes`); shell scripts must stay LF.

## Developing from inside the sandbox

This repository is often developed from inside the sandbox it builds:

- Network goes through the allowlist proxy. `index.crates.io` / `static.crates.io` may be allowed, `docs.rs` and
  `crates.io` usually are not: read crate sources in `~/.cargo/registry/src`. Only the user can allow hosts (on the host).
- `.sandbox/` is hidden (empty) or read-only (`protect_sandbox`); with `workspace = "ro"` the whole project is read-only. Then build in a copy and hand the user a patch. Put it on the user's desktop.
- With `podman = true` under `[tools]` (rootless Podman host), the app can be tried in itself: in a writable copy
  (e.g. under `/config`), `./sandbox up` starts a nested sandbox. The copy needs `.sandbox/`, so the outer sandbox
  must not hide it (`protect_sandbox = true`). Its hosts must be allowed in the outer allowlist too.
- `.git/` is read-only (`protect_git`): no commits, branches or config changes inside; the user commits on the host.
  Read-only git commands may report "dubious ownership" (use `git -c safe.directory='*'`).
